Adding Labels & Dates to Unsubmitted Information

Three ways to let contributors attach labels and dates to a piece of information before the whole file is submitted — with trade-offs, effort, and a recommendation.

The problem

In the Information sidebar, a contributor builds up a file's information rows in a shared working draft. Most fields (title, text, bias, reliability, credibility) live entirely in memory and are only written to the database on Submit. Two attributes behave differently: Labels and Dates are persisted immediately through their own APIs, and those APIs require the information row to already exist in the database.

The result: as soon as a contributor clicks + Add New Information, the new row exists only client-side. Its + Label and + Add date controls are disabled, with the tooltip "Submit this entry before adding labels / dates." A user who wants to tag brand-new information is forced to submit the entire file first — publishing every other in-progress row alongside it.

Where this lives today

  • app/InformationSidebar.tsx — startNew() creates a client-only row via newInformationId(); isUnsaved gates the label & date controls; persistedIds tracks which rows exist in the DB.
  • app/useFileDraft.ts — the shared working snapshot; save() stages a draft, submit() publishes all information rows.
  • …/information/route.ts — POST → addInformation() already persists a single row and accepts a client-supplied id.
  • …/information/[infoId]/labels/route.ts, …/information/[infoId]/datetimes — label & date APIs that 404 for a row that isn't in the DB yet.

Design constraints

  • Don't force a full submit. Tagging one new row must not publish the file's other in-progress rows.
  • Preserve draft semantics. The Save/Submit model in useFileDraft is the backbone of collaborative editing (issue #78); a solution should fit it, not fight it.
  • Respect the check-out lock. Writes only happen while the file is held by the current user (isHeldByMe && !lockedByOther).
  • No orphans / no surprises. Rows the user abandons shouldn't silently accumulate in the database, and history/version behavior should stay coherent.

The three options

1

Create an empty information row on "Add New Information"Recommended

When the user clicks + Add New Information, immediately POST a blank row to …/information (which already accepts a client-supplied id), then add that id to persistedIds. The row now exists in the database, so the label and date APIs work right away — while the row's content fields continue to flow through the normal draft Save/Submit path. Critically, this persists only the one new row; the file's other draft rows are untouched. 

// InformationSidebar.tsx — startNew()
async function startNew() {
  const id = newInformationId(projectId, file.id);
  draft.upsertInformation({ id, informationTitle: "", /* …blanks… */ selections: [] });
  setItemLabels(prev => new Map(prev).set(id, []));
  setSelectedId(id);

  // NEW: register the empty row in the DB so labels/dates attach immediately.
  try {
    await addInformation(projectId, file.id, id, /* empty fields */);
    setPersistedIds(prev => new Set(prev).add(id));   // unlocks the gate
  } catch { /* leave row client-only; gate stays closed, as today */ }
}

The isUnsaved gate then evaluates false for the new row, so + Label and + Add date light up with no other UI change. On Submit, the existing publish path reconciles the same id (an upsert), so the content the user typed lands on the row that already holds the labels/dates.

Pros

  • Directly satisfies the requested design.
  • Reuses the existing single-row addInformation endpoint and the persistedIds machinery — small, localized change.
  • Labels & dates, field history, and PDF selections all "just work" for new rows — no special-casing.
  • No change to the Save/Submit contract.

Cons / risks

  • Orphan rows. A user who adds a row then closes without submitting leaves an empty published row. Needs cleanup (delete-on-abandon, or a "blank + no labels/dates" sweep).
  • Blurs the "nothing is real until Submit" mental model — a row now exists before its content is published.
  • The empty row is visible to other contributors immediately (it's published), even before the author fills it in.
  • Needs a check-out guarantee so the eager POST can't 409.
Effort: Low–Medium Backend change: Minimal (endpoint exists) Risk: Orphan cleanup is the main open question
2

Carry labels & dates in the draft snapshot

Stop persisting labels and dates through their own immediate APIs. Instead, add them to the working snapshot in useFileDraft — exactly like every other information field — and write them to the database as part of save() and submit(). A row no longer needs to exist in the DB to hold staged labels/dates, so the isUnsaved gate disappears entirely. 

// FileDraftSnapshot.information[n] gains:
labels: string[];              // label ids, staged
datetimes: DatetimeInput[];    // staged date payloads

// submit() publishes rows + their labels + their datetimes in one transaction.

This makes the data model uniform: everything about a piece of information is part of one atomic draft that Saves and Submits together.

Pros

  • Conceptually the cleanest — one consistent persistence path for the whole row.
  • No orphan rows; nothing hits the DB until Save/Submit, matching today's mental model.
  • Labels/dates become undoable via Discard Draft, like other fields.
  • Works offline / while composing, with no per-keystroke network calls.

Cons / risks

  • Largest change. Touches the snapshot type, the draft store, the submit transaction, and the server publish logic.
  • Labels/dates currently persist instantly and independently of check-out — this re-couples them to Save/Submit, a behavior change for existing rows.
  • Date records have their own identity/history on the timeline; folding them into the draft needs care so timeline references stay stable.
  • Higher regression surface across the draft, timeline, and label features.
Effort: High Backend change: Significant (submit path) Risk: Broad regression surface
3

Lazy just-in-time persistence on first tag

Keep rows client-only by default, but the first time the user clicks + Label or + Add date on an unsaved row, transparently persist that single row first (the same addInformation POST as Option 1), then perform the label/date call. The gate is replaced by an on-demand promotion: nothing is written to the DB until the user actually needs it there. 

async function ensurePersisted(id: string) {
  if (persistedIds.has(id)) return;
  await addInformation(projectId, file.id, id, currentFieldsFor(id));
  setPersistedIds(prev => new Set(prev).add(id));
}
// handleAddLabel / setDatetimeEditor("new") await ensurePersisted(selectedId) first.

Pros

  • Only creates DB rows the user actually tags — far fewer orphans than Option 1.
  • No new controls; the disabled state simply becomes "works on click."
  • Reuses existing endpoints; medium-sized, mostly client-side change.

Cons / risks

  • Does not match the specifically requested "empty row on create" design.
  • A subtle latency/async moment on first tag (row must be created before the label lands); needs optimistic UI + rollback.
  • Still creates a partially-published row mid-draft — same "visible to others early" concern as Option 1, just deferred.
  • Promotion logic (which fields to send at promote time, keeping them in sync with the draft afterward) adds a reconciliation edge case.
Effort: Medium Backend change: Minimal (endpoint exists) Risk: Async ordering edge cases

Recommendation

Option 1 is the recommended path. It is the design the request calls for, it reuses machinery that already exists (the single-row addInformation endpoint and the persistedIds gate), and it keeps the change small and local to InformationSidebar.tsx. The one problem it must answer is orphan rows: pair it with a cleanup rule — e.g. delete the row on close if it was never given a title, labels, dates, selections, or text — so abandoned blanks don't pile up.

If the team later wants to eliminate the immediate-write inconsistency at its root, Option 2 is the cleaner long-term destination; Option 1 does not block it. Option 3 is a reasonable middle ground if orphan rows prove hard to manage but the full draft rework of Option 2 is too costly.
