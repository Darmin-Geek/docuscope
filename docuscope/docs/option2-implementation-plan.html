Implementation Plan · DocuScope · Option 2

Carry Labels & Dates in the Draft Snapshot

Make labels and dates part of a file's working draft so they can be attached to brand-new, unsubmitted information — persisting them on Submit alongside everything else, and removing the isUnsaved gate entirely. No changes to the information_labels or information_datetimes tables.

The goal

Today, labels and dates are written to the database immediately through their own APIs, which require the information row to already exist. A row created with + Add New Information is client-only until Submit, so its + Label and + Add date controls are disabled with "Submit this entry before adding…". This plan folds labels and dates into the same working snapshot that already carries every other information field, so they persist through Save/Submit and the gate disappears.

Why this needs no schema change
  • The information_labels and information_datetimes tables are untouched — we only change when and through which path their rows are written (inside the existing Submit transaction, instead of via immediate APIs).
  • The draft lives in file_drafts.snapshot, a jsonb column typed only in TypeScript ($type<FileDraftSnapshot>()). Adding fields to FileDraftSnapshot is a type edit, not a migration.

The change, file by file

1

Extend the snapshot type

lib/projects.ts · lib/drizzle/schema.ts (kept mirrored)

Add two fields to each information[] entry in FileDraftSnapshot:

labels: string[];                       // assigned label ids
datetimes: Array<{
  id: string;                           // stable id (existing DB id, or client UUID)
  isRange: boolean;
  startValue: string; startPrecision: Precision;
  endValue: string | null; endPrecision: Precision | null;
}>;

Store only the raw datetime input — no lowerMs/bounds. Bounds are always re-derived server-side, matching the existing rule that a client can never persist inconsistent bounds. Each datetime keeps a stable id so timeline_entries pins survive a submit.

2

Seed labels & dates when loading the draft

app/useFileDraft.ts — loadPublished()
  • Labels: already returned by getInformation() as info.labels — carry them onto each snapshot row.
  • Datetimes: call getDatetimes(projectId, fileId, info.id) per row (alongside the existing getSelections), mapping DB rows down to the raw { id, isRange, startValue, startPrecision, endValue, endPrecision } shape.
  • emptySnapshot() and the post-submit() re-seed both get labels: [], datetimes: [].
3

Add draft mutators

app/useFileDraft.ts

New entries on the FileDraft API, each mutating snapshot, setting dirty, clearing status — the same pattern as upsertSelection:

  • setInformationLabels(infoId, labelIds) (or add/remove helpers)
  • upsertDatetime(infoId, datetime) / removeDatetime(infoId, datetimeId)

Also expose baselineInfoIds: Set<string> (ids present in the published baseline) so the UI can still tell "never-submitted" rows apart — now needed only for field-history visibility, not for labels/dates.

4

Reconcile labels & dates on Submit

lib/projects.server.ts — submitDraft()

Inside the existing transaction, per information row (after the row + selections upsert), reconcile by id exactly like selections:

  • Labels: read current information_labels for the row → delete ids absent from the snapshot, insert…onConflictDoNothing() ids present.
  • Datetimes: for each snapshot datetime, validate + derive bounds, then insert…onConflictDoUpdate({ target: id }); delete stored datetimes whose id is absent from the snapshot. Upserting by id preserves timeline_entries pins; deletions cascade their pins (intended).

Extract/export the private validateAndDerive from timelines.server.ts into a shared helper so submitDraft can reuse it — no logic change, just an export. A staged datetime is already validated by DatetimeEditor before it enters the snapshot, but the server still guards (throws Invalid → the whole submit rolls back).

saveDraft needs no label/date logic — it just stores the jsonb, so staged labels/dates round-trip through the draft and are undone by Discard Draft for free.

5

Rewire the sidebar to the draft

app/InformationSidebar.tsx
  • Delete the itemLabels, persistedIds, and datetimes local state plus the immediate-API effects; read appliedLabels/datetimes straight from selectedItem in the draft.
  • handleAddLabel/handleRemoveLabel → draft.setInformationLabels(...). handleSaveDatetime/handleDeleteDatetime → draft.upsertDatetime/removeDatetime (mint a client UUID for a new date via crypto.randomUUID()).
  • Remove isUnsaved gating and the "Submit this entry before adding…" tooltips/disabled on + Label and + Add date; keep only the check-out gate (isHeldByMe && !lockedByOther).
  • FieldHistoryButton hidden= switches from isUnsaved to "row not in draft.baselineInfoIds" (history genuinely doesn't exist until first submit).
  • startNew() no longer needs label-map seeding.
6

Leave the immediate REST routes in place

app/api/.../information/[infoId]/labels · .../datetimes

After this change the label/datetime POST/PATCH/DELETE routes are unused by the app (only getDatetimes reads remain — used here and in TimelineView). Leave the routes as-is to keep the diff contained; removing them is optional follow-up. TimelineView is unaffected: it reads submitted datetimes and pins them by id.

7

Tests

tests/
  • Server unit: submit a draft that adds labels + datetimes to a new row → assert information_labels/information_datetimes rows. Then submit with one removed and one edited → assert reconciliation, and that an unchanged datetime keeps its id (pin survival).
  • UI: create new information, add a label and a date before any submit, Submit, reload → both persist. Discard Draft drops staged labels/dates.

Trade-offs to confirm

Intended behavior change

  • Labels/dates stop persisting instantly — they now save only on Save (to the draft) and Submit (to the tables). This is the whole point of Option 2 and is exactly what unblocks unsubmitted rows.

Watch-outs

  • Pinning a brand-new date to a timeline requires a Submit first (its id isn't in the DB until then) — the same practical constraint as today.
  • Datetime reconciliation must upsert by id, never delete-and-reinsert, or timeline pins break.
