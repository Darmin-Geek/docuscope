Implementation Plan

Issue #27 — Let users customise what the search bar searches

Today the full-text search box always searches everything — file metadata, PDF contents, and information entries — in a single fixed query. This plan adds a configurable search scope so a user can narrow the search to any subset of those fields (e.g. only author, or only information text + file contents). Default behaviour is unchanged: search everything.

1 · Goal & requirements

  • Default = everything. With no configuration the bar searches all fields, exactly as it does now.
  • Any subset. The user can pick one field, several fields, or a whole category — not just "one or all".
  • Grouped + expandable. Toggle high-level categories (File details, File contents, Information), and expand a category to fine-tune individual fields.
  • Persistent per user, easy to reset. The choice is remembered in localStorage per browser, with a one-click "Search everything again" reset.
  • Folder-ready. Field scope only for now, but the data shape and UI leave an obvious slot for a future "limit to folders" control (issue mentions it).

2 · How search works today

The search term flows: FilesTable input → ProjectView (debounced 300 ms) → getFiles(projectId, folderId, search) client wrapper → GET /api/projects/[id]/files?q=… → getFiles() server → ftsCondition(q).

ftsCondition in lib/projects.server.ts is the heart of it. It ORs three things together, so a file matches if any area matches: 

or(
  // 1. file metadata tsvectors
  (author_tsv || overall_bias_tsv || source_tsv ||
   file_reliability_tsv || file_credibility_tsv) @@ plainto_tsquery(q),
  // 2. PDF body text chunks
  EXISTS (SELECT 1 FROM file_chunks WHERE file_id = files.id
          AND content_tsv @@ plainto_tsquery(q)),
  // 3. information entries
  EXISTS (SELECT 1 FROM information WHERE file_id = files.id
          AND (title_tsv || text_tsv || overall_bias_tsv ||
               reliability_tsv || credibility_tsv) @@ plainto_tsquery(q)),
)

All the searchable tsvector columns already exist (see lib/drizzle/schema.ts). No schema migration is required — this feature only changes which of these existing predicates we emit.

3 · The scope model (shared by all UIs)

Every UI idea below drives the same underlying data structure, so the UI can be swapped without touching the backend contract. A scope is a set of enabled field keys, grouped into three categories:

CategoryField keysBacking column(s)
File details (metadata) author, source, fileBias, fileReliability, fileCredibility files.*_tsv
File contents contents file_chunks.content_tsv
Information infoTitle, infoText, infoBias, infoReliability, infoCredibility information.*_tsv

The scope is serialised onto the request as a single repeatable/CSV param, e.g. ?q=brazil&fields=author,source,contents,infoText. Absent fields param = search everything (the default, and the back-compat path). The server maps each enabled key to its predicate and ORs only those together.

A "filename" key could be added later (filename is not currently in the FTS at all); noting it here but leaving it out of scope to avoid behaviour change.

5 · Backend changes

Touch only lib/projects.server.ts and the route handler.

  1. Define the field keys & predicate map. Add a SearchField union type and a helper that, given a set of enabled keys, builds the corresponding SQL predicates. Each metadata field maps to its own files.*_tsv @@ plainto_tsquery; contents maps to the file_chunks EXISTS; the info keys map to selected columns in the information EXISTS.
  2. Refactor ftsCondition(q) → ftsCondition(q, fields?). When fields is undefined or empty, emit the current "everything" OR (unchanged behaviour). Otherwise emit only the predicates for the enabled keys, still OR-ed together. Build the three information sub-columns and the metadata columns conditionally so we never reference a disabled field.
  3. Thread fields through getFiles(). Add an optional fields?: SearchField[] parameter; pass it to ftsCondition. No change to the folder/no-search branches.
  4. Parse the param in the route. In app/api/projects/[id]/files/route.ts, read searchParams.get('fields'), split on commas, validate each against the known key set (drop unknown keys), and pass the resulting array. Missing param ⇒ pass undefined ⇒ search everything. 
// sketch
type SearchField =
  | 'author' | 'source' | 'fileBias' | 'fileReliability' | 'fileCredibility'
  | 'contents'
  | 'infoTitle' | 'infoText' | 'infoBias' | 'infoReliability' | 'infoCredibility';

function ftsCondition(q: string, fields?: SearchField[]) {
  const all = !fields || fields.length === 0;
  const on = (f: SearchField) => all || fields!.includes(f);
  const parts = [];

  const metaCols = [
    on('author')          && filesTable.authorTsv,
    on('source')          && filesTable.sourceTsv,
    on('fileBias')        && filesTable.overallBiasTsv,
    on('fileReliability') && filesTable.fileReliabilityTsv,
    on('fileCredibility') && filesTable.fileCredibilityTsv,
  ].filter(Boolean);
  if (metaCols.length) parts.push(sql`(${joinWithDoublePipe(metaCols)}) @@ plainto_tsquery('english', ${q})`);

  if (on('contents')) parts.push(sql`EXISTS (… file_chunks …)`);

  const infoCols = [/* infoTitle → titleTsv, … */].filter(Boolean);
  if (infoCols.length) parts.push(sql`EXISTS (… information with (${joinWithDoublePipe(infoCols)}) …)`);

  return or(...parts);
}

Edge case: if a non-empty fields set somehow yields zero predicates (all keys unknown), treat it as "everything" or as "match nothing" — pick match nothing so an explicit empty scope returns no rows rather than silently widening. The UI prevents reaching zero by disabling the last checkbox or auto-resetting.

6 · Frontend changes

  • New SearchScope type & default in lib/projects.ts (shared client/UI types live here), plus the fields param added to the client getFiles() wrapper (only appended to the URL when the scope is narrower than "everything").
  • New component SearchScopeMenu.tsx (Idea A): the Scope button + popover with preset segment, grouped tri-state checkboxes, expanders, and the reset link. Pure controlled component — takes scope + onScopeChange.
  • Wire into FilesTable.tsx next to the existing <input type="search">, and lift scope state into ProjectView.tsx alongside searchQuery/debouncedSearch.
  • Re-fetch on scope change. Add scope to the useEffect dependency array that calls getFiles (no debounce needed — toggles are deliberate), so results update immediately when scope changes.

7 · Persistence & reset

  • Persist under a namespaced key, mirroring the existing docuscope:selectedProjectId convention — e.g. docuscope:searchScope. Store the enabled-keys array as JSON; load it on mount, fall back to the "everything" default on any parse error or absence.
  • Easy reset. A "Reset to everything" / "Search everything again" action clears the stored scope (or sets it to the full set) and returns the UI to default. The button is always visible in the popover footer. Optionally show a small "scope: 2 fields" indicator on the Scope button so a narrowed state is never invisible.
  • Keep it per-browser (localStorage) for now; the server contract (fields param) is already the same one a future per-project DB-backed setting would use, so upgrading later is additive.

8 · Designed for future folder restriction

Folder scope is intentionally out of this change, but the design leaves a clean slot:

  • The request already carries folderId; a future folder restriction becomes a parallel folders=id1,id2 param consumed in the same getFiles branch — no rework of the field-scope plumbing.
  • In the UI, the scope popover (Idea A) or settings panel (Idea C) gains a "Folders" section beneath the field groups, using the same tri-state checkbox pattern fed by the existing FolderTree data.
  • The SearchScope type can grow a folders?: string[] field without breaking the field-only callers.

9 · Testing

Extend tests/search.test.ts (it already has server-side unit tests + UI tests).

  • Server: seed a file whose term appears only in author, another only in PDF contents, another only in an information text. Assert that scoping to author returns only the first, contents only the second, and a combined scope returns the union.
  • Default unchanged: no fields param returns the same set as today (regression guard on back-compat).
  • Empty/invalid scope: unknown keys are dropped; an all-unknown set returns no rows (per the chosen edge-case rule).
  • UI: toggle a category off, assert a known-only-in-that-category file disappears; click reset, assert it returns. Assert the scope survives a reload (localStorage).
