1. Overview

Today a piece of information (a claim extracted from a file) carries text, bias, reliability and credibility, but has no notion of when it happened. This feature lets users tag information with one or more datetimes — each a point or a range, each carrying its own precision (minute → decade → century …) — and then visualise those datetimes on timelines.

  • A Timeline button sits at the top-right of ProjectView, next to search.
  • The timeline view lets users create timelines, open them, and add information entries.
  • Each entry renders above a black time axis as a bar labelled with the information title.
  • Certain spans are solid; uncertain (imprecise) margins are semi-transparent.
  • Overlapping entries stack into lanes, higher up the page.
  • The view zooms to focus on a slice of time; clicking an entry opens that information.

2. Confirmed decisions

  • Multiple datetimes per information. Each information row owns 0..N datetime entries.
  • Project-scoped, many-to-many. Timelines belong to a project; one info can appear on many timelines and a timeline holds many info.
  • Any historical / ancient dates. Storage must not be tied to modern-only epoch assumptions.
  • Imprecision drawn as a faded span. A decade-precision date fills its whole decade, semi-transparent; precise ranges render as a solid opaque bar.

3. Datetime & precision model

The core idea: the user enters a human value plus a precision, and we derive a lower bound and upper bound instant from it. The timeline only ever needs those two numbers to draw; the raw input is kept for editing and display.

Precision levels

A datetime endpoint is a value truncated to a precision. The precision determines how wide the uncertainty window is:

PrecisionUser entersLower boundUpper bound (exclusive)
minute1994-07-08 13:4513:45:0013:46:00
hour1994-07-08 13:0013:00:0014:00:00
day1994-07-08day startnext day
month1994-07month startnext month
year1994Jan 1 1994Jan 1 1995
decade1990sJan 1 1990Jan 1 2000
century1900sJan 1 1900Jan 1 2000

Point vs. range

  • A point has one endpoint. It draws as a single faded band spanning that endpoint's [lower, upper] precision window (a precise minute is a thin band; a decade is a wide one).
  • A range has a start endpoint and an end endpoint, each with its own precision. It draws as:
    • solid bar = [mid(start), mid(end)] — from each endpoint's best-guess instant, the midpoint of its precision window (noon for a day, mid-year for a year). Its two ends are the range's endpoints.
    • start precision line — a faded whisker extending outward (leftward, into the past) from the solid bar's left end out to start.lower, i.e. over the half-window [start.lower, mid(start)].
    • end precision line — a faded whisker extending outward (rightward, into the future) from the solid bar's right end out to end.upper, i.e. over the half-window [mid(end), end.upper].
Precision lines go out from the endpoints, and the two ends are independent. The whisker at each end is sized by that end's precision, so a range can have a long fuzzy start and a sharp end (or vice-versa). Examples:
  • "The 1990s" (point) → one wide faded band, no solid bar.
  • "8 Jul 1994 13:45 → 14:30" (minute/minute) → a solid bar with two whiskers so short they read as sharp caps — effectively a clean solid line.
  • "Sometime in the 1980s until March 1995" (decade start, month end) → solid bar from mid-1985→mid-March 1995, a long faded whisker reaching back to 1980 on the left, and a short faded whisker out to April 1995 on the right.

Storing ancient dates

JS Date and epoch-millisecond bigint comfortably cover roughly 271,000 BC – 275,000 AD, which spans all human history. To stay safe and precision-explicit we store each bound as a signed bigint of epoch-milliseconds computed with a proleptic-Gregorian helper, independent of the browser's local Date quirks. Sorting and range math are plain integer comparisons.

Deep-time note: if geological ranges (millions of years) are ever needed, epoch-ms overflows human intuition long before it overflows bigint, but tick labelling would need a "years-only" mode. Out of scope for v1; the precision enum leaves room to add era/mya later without a data migration of existing rows.

4. Database schema lib/drizzle/schema.ts

Three new tables. Datetimes hang off information; timelines are project-scoped; a join table wires them together many-to-many.

// A datetime attached to a piece of information. Point or range; each endpoint
// carries its own precision. lower/upper bounds are derived on write (epoch ms,
// signed bigint) so the timeline can draw with pure integer math.
export const informationDatetimes = pgTable('information_datetimes', {
  id: uuid('id').primaryKey().defaultRandom(),
  informationId: uuid('information_id').notNull()
    .references(() => information.id, { onDelete: 'cascade' }),
  isRange: boolean('is_range').notNull().default(false),

  // raw input, kept for editing/display
  startValue: text('start_value').notNull(),           // ISO-ish canonical string
  startPrecision: text('start_precision').notNull(),   // minute|hour|day|month|year|decade|century
  endValue: text('end_value'),                         // null when !isRange
  endPrecision: text('end_precision'),

  // derived bounds (epoch ms, proleptic Gregorian) — what the timeline draws
  lowerMs: bigint('lower_ms', { mode: 'bigint' }).notNull(),  // start.lower
  upperMs: bigint('upper_ms', { mode: 'bigint' }).notNull(),  // end.upper (or start.upper for a point)
  coreLowerMs: bigint('core_lower_ms', { mode: 'bigint' }),   // start.upper (range only)
  coreUpperMs: bigint('core_upper_ms', { mode: 'bigint' }),   // end.lower   (range only)
}, (t) => [
  index('info_datetimes_info_idx').on(t.informationId),
  index('info_datetimes_bounds_idx').on(t.lowerMs, t.upperMs),
]);

// A named timeline within a project.
export const timelines = pgTable('timelines', {
  id: uuid('id').primaryKey().defaultRandom(),
  projectId: uuid('project_id').notNull()
    .references(() => projects.id, { onDelete: 'cascade' }),
  title: text('title').notNull(),
  description: text('description'),
  // Default view restored whenever the timeline is opened. defaultStartMs is the
  // left edge (the "default start date"); defaultSpanMs is the window width (the
  // "default zoom"). Both null ⇒ fall back to fit-all. User-editable.
  defaultStartMs: bigint('default_start_ms', { mode: 'bigint' }),
  defaultSpanMs:  bigint('default_span_ms',  { mode: 'bigint' }),
  createdAt: bigint('created_at', { mode: 'number' }).notNull(),
}, (t) => [index('timelines_project_idx').on(t.projectId)]);

// Which information (via a specific datetime) sits on which timeline.
// Pinning a datetime — not just an information — lets an info with several
// datetimes place each one, or the same info on several timelines.
export const timelineEntries = pgTable('timeline_entries', {
  timelineId: uuid('timeline_id').notNull()
    .references(() => timelines.id, { onDelete: 'cascade' }),
  datetimeId: uuid('datetime_id').notNull()
    .references(() => informationDatetimes.id, { onDelete: 'cascade' }),
}, (t) => [primaryKey({ columns: [t.timelineId, t.datetimeId] })]);

Run npm run db:generate then commit the migration; npm run db:push for the local Docker Postgres used by tests.

5. API endpoints app/api/**/route.ts

Client wrappers in lib/timelines.ts; Drizzle implementations in lib/timelines.server.ts (mirrors the projects split). All routes verify the id_token and check the caller contributes to the project.

Bounds are derived server-side in a shared lib/datetimePrecision.ts (also imported by the client for live preview) — single source of truth, unit-testable in isolation.

6. UI / UX flows

6.1 Tagging information with a datetime

In InformationSidebar.tsx, add a "Dates" section under the existing fields: a compact row per datetime (with edit / delete), and an "+ Add date" button that opens the datetime editor designed in §6.4. Each saved row shows a one-line human summary, e.g. "the 1980s → March 1995".

6.2 Opening the timeline view

A Timeline button in the ProjectView top bar (top-right, beside the search box) opens a full-screen TimelineView, layered like the existing project workspace rather than a modal:

  • Left rail: list of the project's timelines + "New timeline" (opens CreateTimelineModal).
  • Main: the selected timeline's canvas, or an empty state prompting creation.
  • "Add information" opens a picker (reuses the search box) to attach an info's datetime(s) to this timeline.

6.4 Datetime entry UI element requirement 3

This is the popover opened by "+ Add date". It must let a user enter a point or a range, pick a precision per endpoint, and understand the consequence before saving. Design principles:

  • Precision-first, adaptive fields. The precision selector is a segmented control (Minute · Hour · Day · Month · Year · Decade · Century). Choosing it decides which inputs appear — pick Year and only a year box shows; Decade shows a "1990s" box; Minute shows date + time. No irrelevant fields are ever visible.
  • Point ↔ Range toggle. In Range mode a second endpoint block appears with its own independent precision selector — directly modelling "ends can have different precisions".
  • BC/AD & big years. The year field is a plain signed integer with a BC/AD toggle, so ancient dates need no special calendar widget.
  • Live preview. A read-only strip mirrors exactly what the timeline will draw — the solid bar plus outward precision whiskers — plus a plain-English sentence. It updates on every keystroke.
  • No separate caption. The bar on the timeline is labelled by the information's title, so the editor never asks for one — it only captures the date itself.

6.3 The timeline canvas

  • A black horizontal axis near the bottom with tick marks and time labels; tick granularity adapts to zoom — see §6.3.2.
  • Entries render above the axis as bars; each shows its information title.
  • Zoom via scroll-wheel / +/− buttons / drag-to-select a region. A "Fit all" button frames every entry.
  • Click an entry → open the information view (the existing InformationSidebar for that info's file), so the timeline is a navigation surface into the corpus.

6.3.2 Adaptive time scale (zoom reveals finer units) requirement

The axis is not fixed to years. As the user zooms in, the labels step down through calendar units so there are always ~6–10 readable ticks: centuries → decades → years → months → days → hours → minutes. Ticks snap to real calendar boundaries (the 1st of a month, midnight of a day, the top of an hour) rather than arbitrary offsets, and major boundaries are emphasised (a taller/darker tick, e.g. January when showing months, or midnight when showing hours) with the parent unit shown for context.

6.3.3 Default start date & zoom requirement

Each timeline stores its own default view — a start date (left edge) and a zoom level (window width), persisted as defaultStartMs / defaultSpanMs on the timelines row. Opening a timeline restores that view; if unset (e.g. a brand-new timeline) it falls back to "fit all entries".

  • "Set current view as default" button in the canvas toolbar snapshots the present pan+zoom (a PATCH).
  • "Reset to default" jumps back to the saved view at any time.
  • Both values are also editable as explicit fields (a date picker + a zoom/scale selector) in the timeline's settings, so a user can type an exact default start date.

6.3.1 Moving through time (pan) requirement 1

Panning left/right must feel effortless — several redundant ways, all sliding the [viewLo, viewHi] window by a delta while keeping its width (the zoom level) fixed:

  • ◀ / ▶ arrow buttons flanking the canvas (and repeat-on-hold) step the view by ~⅓ of the visible span — an obvious, discoverable control.
  • Keyboard ← / → when the canvas is focused; Shift jumps a full span, Home/End leap to the first/last entry.
  • Click-drag the canvas background (grab cursor) to slide the view directly; Shift + scroll-wheel pans horizontally (plain wheel still zooms).
  • Overview scrollbar / mini-map under the axis: a thin strip showing the whole data span with a draggable window handle, so users always see where they are and can leap anywhere.

Pan is clamped to the data span (plus a small margin) so users can't get lost in empty time; the mini-map handle makes the current position explicit.

7. Rendering algorithm

  1. Scale. The visible window [viewLowerMs, viewUpperMs] maps linearly to pixel x. Zoom changes the window's width; pan slides it (§6.3.1).
  2. Geometry. A range draws a full-height solid bar over [coreLower, coreUpper], then a faded precision whisker extending outward from each end — left whisker over [lower, coreLower], right whisker over [coreUpper, upper] — each sized by its own endpoint's precision, so the two can differ. A point draws a single faded band over [lower, upper]. Whiskers are thinner than the bar and mid-aligned so they read as "lines out of the endpoints"; a zero-width whisker (precise end) collapses to a sharp cap.
  3. Lane packing (overlap → stack up). Sort entries by lower. Greedily assign each to the lowest lane whose last bar ends before this bar starts (compare in pixels, including whiskers and label width, so touching bars don't collide). New lanes stack upward from the axis. This is the classic interval-partition/greedy-colouring approach.
  4. Adaptive ticks. Pick the tick unit from the visible span (§6.3.2): year "nice" steps when wide, otherwise months → days → hours → minutes, each snapped to calendar boundaries with major boundaries emphasised.
  5. Draw. Axis + adaptive ticks first, then each entry at y = axisY − (lane+1)*laneHeight: whiskers at ~35% opacity, solid bar at full opacity, title clipped to the bar (tooltip on hover for the full title).
function assignLanes(entries /* sorted by lowerPx */) {
  const laneEnds = [];               // rightmost px used per lane
  for (const e of entries) {
    let lane = laneEnds.findIndex(end => end < e.leftPx - GAP);
    if (lane === -1) { lane = laneEnds.length; laneEnds.push(0); }
    laneEnds[lane] = e.rightPx;      // includes label width
    e.lane = lane;
  }
  return laneEnds.length;            // total lanes = canvas height
}

9. Edge cases

  • Reversed range (end before start): validate on save; offer to swap.
  • Different precision per end (e.g. start precise to the day, end to the decade): handled by design — the right-hand whisker just grows to a decade while the left stays a sharp cap.
  • Info with several datetimes on one timeline: each pinned datetime is its own bar, all sharing the same information title.
  • Deleting information / datetime: cascade removes timeline entries (FK onDelete: cascade).
  • Empty timeline / all entries off-screen: show an empty state and a "Fit all" nudge.
  • Extreme zoom: clamp minimum window (e.g. one minute) and maximum (data span ×50) to avoid divide-by-tiny.
  • Timezone: store and draw in UTC to keep bounds stable across users; display "UTC" on hover for sub-day precision.

10. Testing tests/

  • Unit — lib/datetimePrecision.ts: value+precision → correct [lower, upper] for every level, including BC years and decade/century boundaries.
  • Unit — lane packing: non-overlapping bars share a lane; overlaps stack; label width forces a new lane.
  • Unit — adaptive ticks: the chosen unit steps from years → months → days → hours → minutes across shrinking spans, and ticks snap to calendar boundaries (month starts, midnight, top-of-hour).
  • Server (Drizzle, Docker Postgres): create timeline, attach/detach datetime, cascade on info delete, project-scoping (can't attach cross-project info), and persist/read back defaultStartMs / defaultSpanMs.
  • Playwright UI: Timeline button opens the view; create a timeline; add a dated info; assert a bar with the title appears; click it opens the information sidebar; zooming in reveals month/day/hour labels; "Set default view" then reload restores that pan+zoom.
  • Follow existing patterns: db-helpers.ts to seed, injectOidcUser() for auth.
