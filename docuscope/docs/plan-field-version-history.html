Field Version History

Version history for every text/metadata field of File Details and Information, surfaced via a clock icon next to each field label. Each version shows the value and the display name of who made that edit.

Confirmed decisions
Capture model
Per-field, on Submit. Compare old vs. new per field; write a version row only for fields that actually changed.
Field scope
Text/metadata fields only. Labels and PDF selections are out of scope.
Attribution
Display name, captured at Submit time and stored denormalized.
UI surface
A small clock icon beside each field label; click opens a compact popover, newest first.

1. Why Submit is the capture point

Field edits are staged in a per-user working draft and only become "official" when submitDraft writes them into the files / information tables in one transaction (lib/projects.server.ts:908). That handler already knows the acting user (uid, email) and is the single chokepoint through which published changes flow — Save only touches the private draft, so it is intentionally not versioned. Capturing there means:

  • One consistent attribution per published change.
  • No noise from unpublished drafts or per-user intermediate states.
  • Diffing old-vs-new is trivial: we read current rows inside the same transaction before overwriting them.

2. Fields in scope

EntityFields versioned
File
files		 author, createdDate, source, overallBias, fileReliability, fileCredibility, fileReliabilityCode, fileCredibilityCode
Information
information		 informationTitle, informationText, overallBias, informationReliability, informationCredibility, informationReliabilityCode, informationCredibilityCode

All are stored as text in history. createdDate (unix seconds) is stored as its numeric string and formatted as a date in the popover; Admiralty codes are stored verbatim. Excluded: label assignments (saved immediately outside Submit) and PDF selections.

3. Data model

Two tables — one per entity — so each gets a real foreign key with onDelete: 'cascade'. This matters because submitDraft deletes information rows that fall out of the snapshot; their history should disappear with them for free rather than leaking orphans. (A single polymorphic field_versions table was considered but rejected: it can't FK to two parents, forcing manual cleanup.)

Add to lib/drizzle/schema.ts:

export const fileFieldVersions = pgTable(
  'file_field_versions',
  {
    id: uuid('id').primaryKey().defaultRandom(),
    fileId: uuid('file_id')
      .notNull()
      .references(() => files.id, { onDelete: 'cascade' }),
    field: text('field').notNull(),          // 'author' | 'source' | ...
    value: text('value'),                    // new value; null = field cleared
    editorUid: text('editor_uid').notNull(), // Cognito sub
    editorName: text('editor_name').notNull(), // denormalized snapshot at edit time
    createdAt: bigint('created_at', { mode: 'number' }).notNull(), // epoch ms
  },
  (t) => [
    index('file_field_versions_lookup_idx').on(t.fileId, t.field, t.createdAt),
  ],
);

export const informationFieldVersions = pgTable(
  'information_field_versions',
  {
    id: uuid('id').primaryKey().defaultRandom(),
    informationId: uuid('information_id')
      .notNull()
      .references(() => information.id, { onDelete: 'cascade' }),
    field: text('field').notNull(),
    value: text('value'),
    editorUid: text('editor_uid').notNull(),
    editorName: text('editor_name').notNull(),
    createdAt: bigint('created_at', { mode: 'number' }).notNull(),
  },
  (t) => [
    index('information_field_versions_lookup_idx')
      .on(t.informationId, t.field, t.createdAt),
  ],
);

Migration: npm run db:generate then commit the SQL under drizzle/migrations/; npm run db:push to apply to local Docker Postgres for tests.

4. Server: recording versions

4.1 Resolve the editor's name once

submitDraft currently receives uid. Add the editor's display name so it can be stamped on rows. The Submit route (app/api/projects/[id]/files/[fileId]/submit/route.ts) already has uid; resolve the name via getUserProfile(uid) (Cognito) and pass it through. Fall back to the email local-part, then "Unknown", if the profile has no name.

4.2 Diff-and-insert inside the transaction

Extend submitDraft (lib/projects.server.ts:908). Before each overwrite, read the current values, compare per field, and insert a version row for every field whose value changed. Do it in the same tx so history and the published change commit atomically.

// (1) file metadata — read current BEFORE updating
const [current] = await tx.select().from(filesTable)
  .where(and(eq(filesTable.id, fileId), eq(filesTable.projectId, projectId)));

const now = Date.now();
const fileVersionRows = FILE_VERSIONED_FIELDS
  .filter((f) => !valuesEqual(current[f], snapshot.metadata[f]))
  .map((f) => ({
    fileId, field: f, value: toText(snapshot.metadata[f]),
    editorUid: uid, editorName, createdAt: now,
  }));
if (fileVersionRows.length) await tx.insert(fileFieldVersions).values(fileVersionRows);

await tx.update(filesTable).set(snapshot.metadata).where(/* ...unchanged... */);

Do the same per information row in the existing upsert loop: for an existing row, diff against the fetched current values; for a brand-new row, record a baseline version for each non-empty field (see 4.3). valuesEqual treats null and unchanged text as equal so no-op submits write nothing; toText stringifies numbers (e.g. createdDate).

4.3 Baseline / first version

  • New files — in createFileRecord (lib/projects.server.ts:438), insert an initial version for each field that has a value at creation, attributed to the creating user. Files created with blank metadata simply have no baseline, which is fine.
  • New information rows — on first insert during Submit, write a baseline version per non-empty field. This guarantees the very first value is in history, not just subsequent edits.

5. API

One read endpoint per entity, returning all versions for that entity grouped by field. Fetching everything in a single call (rather than per-field) lets the client open any field's popover instantly with no extra round-trip.

MethodRouteReturns
GET/api/projects/[id]/files/[fileId]/historyFile field versions
GET/api/projects/[id]/files/[fileId]/information/[infoId]/historyInformation field versions

Shape (newest first within each field):

type FieldVersion = { value: string | null; editorName: string; createdAt: number };
type FieldHistory = Record<string, FieldVersion[]>;  // keyed by field name

Auth mirrors existing file routes: verifyAuth then requireContributor. History is read-only and available to any contributor regardless of check-out — viewing the past never requires holding the lock. Add client wrappers getFileHistory / getInformationHistory and the FieldVersion/FieldHistory types in lib/projects.ts; server implementations in lib/projects.server.ts.

6. Client UI

6.1 New pieces

  • app/FieldHistoryButton.tsx — a clock icon button rendered beside a field label. Props: the field key and a getter for that field's version list. Toggles a popover.
  • app/FieldHistoryPopover.tsx — lists versions newest-first: the value (blank rendered as (empty), long text clamped with expand), the editor's display name, and a formatted timestamp. Closes on outside-click / Esc.
  • app/useFieldHistory.ts — hook that fetches the entity's history once, caches it, and exposes versionsFor(field). Re-fetches after a successful Submit so freshly published edits appear.

6.2 Wiring into the sidebars

Both sidebars render each field label as a plain <span> (e.g. FileSidebar.tsx:591 "Author", InformationSidebar.tsx:382 "Title"). Wrap each label + icon in a small flex row and drop in <FieldHistoryButton>. The icon is always enabled (read-only), independent of the check-out lock.

Information caveat: a newly-added entry that hasn't been Submitted has no persisted id and no history yet — reuse the existing persistedIds gate (InformationSidebar.tsx:263) to hide the clock icon for unsaved entries, matching how the label picker is already gated.

7. Edge cases

  • No history — popover shows "No previous versions." (current value only, e.g. legacy data with no baseline).
  • No-op Submit — a field resubmitted unchanged writes no row (valuesEqual dedupe).
  • Cleared field — value stored as null, rendered as (empty).
  • Long text (source, information text) — clamp with a "show more" toggle.
  • Unsaved information entry — icon hidden until persisted.
  • Deleted information — its history cascade-deletes via the FK.
  • Editor renamed later — old rows keep the name captured at edit time (denormalized), so history stays historically accurate.
  • Editor with no Cognito name — fall back to email local-part, then "Unknown".

8. Testing

Playwright suite under tests/ against local Docker Postgres (npm test).

  • Server: Submit records a version only for changed fields; unchanged fields write nothing; attribution (uid + captured name) is correct; baseline written on file create and on first information insert; two sequential edits by different users produce two ordered rows.
  • Cascade: deleting an information row (via Submit reconciliation) removes its version rows.
  • UI: clock icon renders next to each in-scope field; popover lists entries newest-first with value + name + time; icon hidden for an unsaved information entry; popover works without holding the check-out.

9. Rollout & work breakdown

  1. Schema: add both tables + indexes; db:generate, commit migration, db:push.
  2. Server capture: thread editorName into submitDraft; diff-and-insert; baselines in createFileRecord and first-insert path.
  3. API: two GET history routes + client wrappers & types.
  4. Client: useFieldHistory, FieldHistoryButton, FieldHistoryPopover; wire into both sidebars.
  5. Tests: server + UI.
  6. Optional backfill: seed one baseline version per existing file/information from current values, attributed to "Unknown / imported", so pre-existing data isn't blank in the popover.
