Issue #78 Builds on #79 (labels) & #86 (manual check-out, issue #77)

Manual Save & Submit

Replace the current auto-save-on-click-away with explicit Save (stages work to a separate draft store) and Submit (publishes the draft into the main tables). Both gated on the user holding the file's check-out.

1 · Goal & behaviour

Today every editable field in the File Details and Information sidebars (and PDF selections) is persisted to the main tables the moment focus leaves it. Issue #78 wants that to stop. Instead:

  • Two buttons — Save and Submit — sit horizontally between the “Overall Credibility” field and the “Open information view” button in the File Details sidebar.
  • Save writes the user's in-progress work to a separate draft store, not the main files/information/information_selections tables. The user may Save at any time.
  • Submit promotes the staged work into the main tables, then clears the draft.
  • Both buttons are disabled unless the current user holds the check-out (isHeldByMe from #86). They are also disabled when another user holds it.
  • Submit must be independently disable-able later (“features which temporarily disable submit until a user is done with a task”) — so its disabled state is driven by a single, extensible predicate.

Confirmed design decisions

ScopeFile metadata + information entries + PDF selections are all staged through Save/Submit.
Click-awayFully manual. Blur no longer writes anything to storage. Only Save (→ draft) and Submit (→ main) persist.
After SubmitClear the draft. Reopening shows the published main-table values until the user edits again.
Draft keyingOne draft per user, per file — PK (file_id, user_id).
Consequence of “fully manual” + scope. Information entries and PDF selections currently hit the server on every add/edit/delete. To make them manual they must become in-memory working state that is only persisted on Save/Submit. This in-memory refactor of InformationSidebar and PdfViewerModal is the largest part of the work — see Phase 4.

2 · Architecture: one JSON draft snapshot per (file, user)

Because the draft spans three tables (file metadata, N information rows, M selection rows per information) and is never searched or queried on its own, the simplest robust store is a single jsonb snapshot of the whole editable payload, keyed by (file_id, user_id). Save overwrites the snapshot; Submit reads it, applies it to the real tables in a transaction, and deletes it.

Draft snapshot shape

type FileDraftSnapshot = {
  metadata: {
    author: string | null;
    createdDate: number | null;      // unix seconds
    overallBias: string | null;
    source: string | null;
    fileReliability: string | null;
    fileCredibility: string | null;
  };
  information: Array<{
    id: string;                       // existing id, or a client-generated UUID for new rows
    informationTitle: string;
    informationText: string | null;
    overallBias: string | null;
    informationReliability: string | null;
    informationCredibility: string | null;
    selections: Array<{
      id: string;                     // existing id, or client UUID for new marks
      pageIndex: number;
      boundingTop: number;
      boundingLeft: number;
      rects: SelectionRect[];
      text: string;
    }>;
  }>;
};

New information rows and new selections get client-generated UUIDs in the snapshot; addInformation already accepts a caller-supplied id, so Submit can insert them with stable ids. This sidesteps the “immediate POST to get a server id” pattern that exists today.

Why not mirror tables (information_drafts, selection_drafts, …)? It triples the schema, needs no FTS, and makes Submit a fiddly per-row diff/insert/update/delete across three tables. The jsonb snapshot keeps drafts as opaque staging and concentrates all reconciliation logic in one submitDraft transaction. Labels and folders stay out of the draft — they already persist immediately and aren't part of the field-editing flow.

3 · Backend

3.1 Schema new table

docuscope/lib/drizzle/schema.ts

export const fileDrafts = pgTable(
  'file_drafts',
  {
    fileId: uuid('file_id')
      .notNull()
      .references(() => files.id, { onDelete: 'cascade' }),
    userId: text('user_id').notNull(),          // Cognito uid (matches files.checked_out_by)
    snapshot: jsonb('snapshot').$type<FileDraftSnapshot>().notNull(),
    updatedAt: bigint('updated_at', { mode: 'number' }).notNull(),
  },
  (t) => [primaryKey({ columns: [t.fileId, t.userId] })],
);
  • onDelete: 'cascade' from files so deleting a file drops stray drafts.
  • No tsvector / GIN indexes — drafts are write-and-read-by-key only.
  • Run npm run db:generate to emit the migration (next number after the merged state of #79/#86, e.g. 0006_file_drafts.sql), then npm run db:push for the local Docker Postgres.

3.2 Server data layer edit

docuscope/lib/projects.server.ts

FunctionBehaviour
getDraft(projectId, fileId, uid)Return the snapshot for (fileId, uid) or null.
saveDraft(projectId, fileId, uid, snapshot)Upsert (onConflictDoUpdate on the PK) the snapshot + updatedAt. Does not touch the main tables.
submitDraft(projectId, fileId, uid, snapshot)Transaction: (1) update files metadata; (2) reconcile information for the file — upsert rows present in the snapshot, delete rows not in it; (3) per information, reconcile information_selections the same way; (4) delete the file_drafts row. Reuses/extends the existing addInformation/updateInformation/deleteInformation/addSelection/deleteSelection helpers inside one db.transaction(...).
discardDraft(projectId, fileId, uid)Delete the draft row (used if we later add a “Discard” affordance; cheap to include now).
Submit takes the snapshot from the request body (the freshest client state) rather than re-reading the stored draft, so a user can Submit work they typed but didn't explicitly Save first. The stored draft is still cleared on success.

3.3 Check-out enforcement

Mirror the #86 guard: every draft/submit mutation verifies the file is checked out by the caller. Factor the repeated check into a helper so it's not copy-pasted:

docuscope/lib/projects.server.ts

// Throws a 409-mapped error unless the file is unheld or held by `uid`.
export async function requireCheckoutHolder(projectId, fileId, uid) {
  const file = await getFile(projectId, fileId);
  if (file.checkedOutBy && file.checkedOutBy !== uid) {
    throw new CheckoutConflictError();   // mapped to 409 in apiError
  }
}

Optional cleanup: retrofit the per-route checkedOutBy checks added in #86 to call this helper. Not required for #78, but keeps the rule in one place.

4 · Frontend

4.1 Shared working state — useFileDraft new

docuscope/app/useFileDraft.ts

Metadata lives in FileSidebar, information in InformationSidebar, selections in PdfViewerModal — three sibling components. They must edit one snapshot so Save/Submit persist everything together. Introduce a hook (held by ProjectView, the common parent, and threaded down as props or via a small context) that owns the working snapshot for the open file:

const draft = useFileDraft({ projectId, file, isHeldByMe });
// draft.snapshot            – current in-memory working state
// draft.dirty               – snapshot differs from last save/load
// draft.setMetadata(patch)  – update file fields
// draft.upsertInformation / removeInformation
// draft.upsertSelection / removeSelection
// draft.save()              – PUT …/draft   (Save button)
// draft.submit()            – POST …/submit (Submit button), then reset from main
// draft.hasDraft            – a stored draft exists for this (file, user)
// draft.conflictsOnCheckout – hasDraft && draft would overwrite a filled field
// draft.applyDraft()        – load the stored draft into the working state
// draft.discardDraft()      – DELETE …/draft, then seed from published values
// draft.saving / draft.submitting / draft.error
  • Initialisation: on open, call getDraft and load the published values (file + getInformation + getSelections). If no draft exists, seed the working snapshot from the published values. If a draft does exist, resolution is deferred to check-out time via the conflict prompt below (until then the read-only view shows the published values). A subtle “Unsaved draft” indicator can show when a draft is present.
  • Submit: on success, clear local dirty state and re-seed from the now-published main values (draft is gone server-side).
  • Check-in interaction: the draft is keyed per user and survives check-in (it's the user's private working copy). Re-checking-out reloads it. (Stated as the default; easy to change to discard-on-check-in if desired.)

4.2 Draft-conflict prompt on check-out new

docuscope/app/DraftConflictModal.tsx

When a user checks out a file for which they already hold a draft and at least one field that field’s draft would overwrite has already been filled in (i.e. the published main-table value is non-empty), they must be asked what to do before editing begins:

  • Use my draft — load the draft snapshot into the working state locally, overwriting the existing (published) field values in the editor only. Nothing is written to the main tables until the user later clicks Submit.
  • Discard my draft — delete the draft (DELETE …/draft via discardDraft) and seed the working state from the published values.

Trigger & placement. Hook this into the Check Out action (the #86 toolbar button). On a successful check-out (lock.acquire() resolves), if getDraft returned a snapshot and the conflict predicate holds, open DraftConflictModal and block field editing until the user chooses. If a draft exists but every field it would replace is currently empty, skip the prompt and just load the draft (nothing is being overwritten).

Conflict predicate

// A draft "overwrites a filled-in field" if, for any field present in the draft,
// the corresponding published value is non-empty and differs from the draft.
function draftOverwritesFilledField(published, draft): boolean {
  const fields = ['author','createdDate','overallBias','source',
                  'fileReliability','fileCredibility'] as const;
  const metaConflict = fields.some(
    (f) => published[f] != null && published[f] !== '' && draft.metadata[f] !== published[f],
  );
  // Information/selection scope: also conflict if published rows exist that the
  // draft would replace (the file already has information/selections on record).
  const infoConflict = publishedInformation.length > 0;
  return metaConflict || infoConflict;
}

Keep the predicate in useFileDraft so both the modal trigger and tests share one definition. The exact information/selection rule is a judgement call — the conservative version above prompts whenever the file already has any published information rows; tighten to per-entry comparison if that proves too eager.

  • Modal: follows the existing modal conventions (e.g. DeleteInformationModal) — title, an explanatory line, and two buttons (“Use my draft” / “Discard my draft”), plus the standard close/escape. It is not dismissible into an ambiguous state: closing without choosing should default to the safe option (keep the draft, fields stay read-only / show published values) so no work is silently lost.
  • Wiring: FileSidebar renders DraftConflictModal and drives it from the check-out handler; the choice calls draft.applyDraft() or draft.discardDraft() on the hook.

6 · Phasing & sequencing

  1. Schema + migration — file_drafts table, generate & push.
  2. Server layer + routes — getDraft/saveDraft/submitDraft/discardDraft, requireCheckoutHolder, /draft & /submit routes; client wrappers. Independently testable via API.
  3. useFileDraft + FileSidebar buttons — metadata-only Save/Submit working end-to-end (smallest vertical slice that satisfies the literal issue).
  4. Information staging — move InformationSidebar to the in-memory snapshot.
  5. Selection staging — move PdfViewerModal to the in-memory snapshot.
  6. Remove auto-save paths — delete blur-to-main writes across the three components.
  7. Tests + polish — draft.test.ts, status/error UI, “unsaved draft” indicator.
Phases 1–3 deliver the issue's headline behaviour for file metadata. Phases 4–5 are the bulk of the effort and exist only because the chosen scope includes information entries and PDF selections.

7 · Risks & open points

  • In-memory refactor of information/selections is the riskiest change — it inverts the current “persist immediately” model. Reconciliation on Submit (upsert present, delete absent) must be transactional to avoid half-published state.
  • Concurrent edits while checked out — check-out is exclusive, so the per-user draft can't be clobbered by another user mid-session; the server guard backstops a stale client.
  • FTS freshness — information/selection tsvectors only update on Submit (when rows actually change), which is the intended behaviour: drafts are not searchable.
  • Future “disable submit until task done” — implemented now as the single submitLocked predicate; the later feature just feeds that flag.
  • Migration numbering assumes #79 (0004_brainy_supreme_intelligence) and #86's checkout work are already merged; regenerate to land on the correct next number.
